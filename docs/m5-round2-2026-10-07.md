## (a) Policy flags in the tooling

**CLI (`src/cli.mjs`).**
- `--targeting-policy <v>` works with `--scenario`, `--domain` and
  `--ensemble`, including the extra `--timeline` seeds.
- `--colony-policy <v>` (from part b) works the same way. The two flags can be
  combined.
- An unknown value, a missing value, or `--civ` with either flag exits
  non-zero.
- Options are passed to the simulation only when a flag is present.

**Ensemble (`src/ensemble.mjs`, `src/report.mjs`).**
- `ensemblePlan(n, {…, targetingPolicy, colonyPolicy})` adds a policy key to a
  task only when that policy is given.
- `runSeed`, the forked worker and `summarizeRun` carry the key through.
- `report.md` gains a `Targeting policy: … (opt-in)` or
  `Colony policy: … (opt-in)` line only when a run has that policy.

**Plausibility (`tools/m4-plausibility.mjs`).**
- It accepts `--targeting-policy`, `--colony-policy` and a test-only
  `--until-year`. `measure` and `render` are exported.
- **Root check.** `measure` throws when the `--root` tree does not apply a
  requested policy (`world.def.<policy>.version` must match). Pre-round-1
  trees silently ignore unknown options, so without this check an "on" run
  could really be an "off" run.
- **Delivered-knowledge count.** When the targeting policy is on, each run row
  and each scenario aggregate gains `launchPriorFailure`. It counts accepted
  LAUNCH events by `params.priorFailure`:
  - one key per reason: `none`, `transit-loss`, `occupied`, `uninhabitable`
    and `colony-died`;
  - `active`, the number of launches where `priorFailureActive = 1`.

  These launches were made with *delivered* failure knowledge. Review 3
  finding 2 asked for this to be counted separately from the omniscient
  `repeatLaunchesToFailedTarget`, which is unchanged.
- The report gains a top-level policy key and a `method` sentence only when a
  policy is set. Default JSON and text bytes are unchanged.

**Tests:** `tests/m5-tooling.test.mjs`, 7 tests. They check:

- the default scenario CLI bytes, pinned by sha256 and equal to an in-process
  `scenarioCLI` call;
- that the flag reaches the manifest;
- the default `--domain` digest;
- rejections;
- that ensemble tasks carry the policy only when it is set;
- `runEnsemble` with `jobs=2`, which equals `runSeed`;
- the report line;
- aggregation and rendering of the plausibility counts;
- a short `measure()` call;
- that the `--timeline` extras carry the flag.

**Clarification of the round 1 doc.** `resultDigest` is a Merkle root over the
history entries only; the manifest is not in it. Opted-in runs also draw the
same variates. So an opted-in run whose history never touches a policy
payload has the **same result digest** as the default run. Round 1 said that
"recipe and result digests still differ". That is true only once a history
contains a launch, failure or founding signal. A short toy-12/toy-1 run
(200 years) shows the equality. The manifest and recipe digests always differ.

### Mechanics

All values are [scenario], in the frozen `COLONY_M5` object in `src/tech.mjs`:

| Constant | Value |
|---|---|
| `reserveInitialYears` | 1000 |
| `reserveCapYears` | 1000 |
| `maxDrainYearsPerTick` | 10 |
| `localRegainYearsPerTick` | 5 |
| `reinforcementYearsPerThousand` | 250 |

- **Option.**
  - `colonyPolicy: 'm5-colony-1'` works on `createDomainDefinition`,
    `createDomain` and `createScenario`. Any other value throws `RangeError`.
    Planet-only paths reject it.
  - When the policy is on, `scenarioPriors.colonyPolicy` and
    `def.colonyPolicy` exist. When it is off, both are absent.
  - `rngManifestDigest` is now the digest of the manifest *before either* M5
    block. It is set when either policy is on. So every on/off combination
    draws the same variates. Targeting-only digests are unchanged:
    `rngManifestDigest` is `6c76fcb7…` and `manifestDigest` is `5956a5ec…`,
    both checked against main efeeb37.
- **Stock.** Colony arcs get a Number field `colonyReserve`, which is absent
  in default runs. It starts at 1000.
  - While the stock is above 0, it credits maintenance exactly as the old
    archive did: `max(neff, limit)`, only for tiers ≤ `foundingTiers` and only
    in living regions.
  - The age test `tick < foundedYear + 1000` is used only when the policy is
    off.
- **Drain.**
  - Pairs considered: every region/domain pair at or below its founding tier.
  - Gap measured: the maintenance population including network support but
    excluding the reserve.
  - Per-tick drain: the maximum over those pairs of `ceil(10·(limit − maint)/limit)`.
  - The stock floors at 0.

  An unsupported colony drains 10 per tick, which is the old 1,000-year
  bridge. A colony with 75% support drains 3 per tick. A fully supported
  colony drains 0.
- **Regain.** A tick with zero drain regains 5, up to the cap of 1000.
- **Deviation from the spec (accepted).** The shortfall is evaluated even when
  the stock is 0. So an unsupported colony stays at 0 instead of cycling
  0 → 5 → 0, which would be a hidden survival boost.
- **Reinforcement.** An accepted same-lineage reinforcement whose voyage tiers
  are ≥ `foundingTiers` in every domain adds `floor(persons·250/1000)`, capped
  at 1000. The change is recorded as an `arc.colonyReserve` set effect plus a
  `data.sets` entry.
  - `validateEvent` allows that one write on COLONY_FOUNDED as an annex
    extension, so the catalogue digest is untouched.
  - `COLONY_ARC_FIELDS` appends `colonyReserve` to the sorted `ARC_FIELDS`.
    It is used only when the field exists, and `WITNESS_VERSION` is unchanged.
- **Domain-qualified STATUS.**
  - When the policy is on, STATUS reports carry
    `qualified[d][k] = Σ pop(regions with tiers[d] ≥ k)`.
  - `maintenancePopulation` then credits `qualified[d][r.tiers[d]]` instead of
    the whole population. The 100‰ link credit, freshness and latest-report
    rules are unchanged.
- **Docs.** `docs/transition-table-v1.md` has a new section, "M5 round 2:
  colony reserve (opt-in)". It sits after the `M2A-WITNESS-ANNEX` marker, so
  `contractDigest` is unchanged.

## (c) Doomed-star starvation risk of the 10,000-year `uninhabitable` resurvey

No simulation was run for this part. It uses only the fixtures, the arrival
predicate and the targeting code.

**When can `uninhabitable` fire?** An arrival is rejected as
`destination-uninhabitable` (`src/domain.mjs`) when either of these is true:

- the host check fails: `habitat-buildable` without tiers[0] ≥ 5 and
  tiers[1] ≥ 5;
- `uninhabitableAt(def, p, t)` is true. Round 2 extracted this function as a
  pure refactor. It is true when the year is before `habitableFromYear`, at or
  after `habitableUntilYear`, at or after `stellarDoomYear + grace`, or in an
  epoch with no Kbase > 0 row.

The host check cannot fail on arrival. `routesFor` checks the same condition
on the launching region's tiers, and the voyage copies exactly those tiers.
So only the time/environment predicate matters.

**Theorem (absorbing windows).**
- Suppose a destination's uninhabitable set is *absorbing*: once it holds, it
  holds until the horizon.
- Then every launch suppressed by the resurvey would itself be rejected.
- The reason is timing. A rejection at arrival year A is reported no earlier
  than A. Any launch that knows about it arrives after A, and from A onwards
  the destination is uninhabitable.

So under an absorbing window the resurvey cannot starve colonisation. Its
first-order effect is to move launch stock to other targets: `weightedPick`
then chooses among the remaining routes. Later trajectories diverge
chaotically, so ensemble differences cannot be attributed to this one rule.

`habitableUntilYear` and stellar doom are absorbing by construction. Only
`habitableFromYear > 0` and a middle-epoch Kbase gap can create a
*temporary* window.

**The scenario fixtures.** `tests/m5-resurvey.test.mjs` scans every domain
scenario. For each one it checks every destination that a habitable or
habitat-buildable route can reach, at every tick from `fromTick` to
`untilTick`. Results:

- Exactly one uninhabitable interval exists in all six domain scenarios:
  doomed-star `stub:s00:b0` (the home world), from year 25,500 (doom 25,000
  plus 500 grace) to the horizon at 30,000. It is absorbing.
- Evacuation targets are never uninhabitable. These are `s00:b1` and `s00:b2`
  (habitat-buildable in the same system, with stellar doom `null`) and
  `s01:b0` and `s02:b0` (temperate, habitable from year 0 to 2,000,000 with
  Kbase > 0).
- So the resurvey can never block an evacuation or colony launch in any
  current scenario.
- In doomed-star, only launches *back* to the dead home world can be
  rejected. These come from colonies at `s00:b1`, `s00:b2` and `s01:b0`.
- A negative self-check confirms the guard has teeth: a later
  `habitableFromYear` and a Kbase-0 middle epoch are both classified as
  temporary, so the assertion fails on them.

**Recorded evidence agrees.** The M4d plausibility record
(`docs/evidence/m4-plausibility-after.json`, policy off, N=30) has 2
`destination-uninhabitable` rejections in doomed-star and none in any other
scenario.

**Off versus on.**
- With the policy off, a rejection at A ≥ 25,500 brings the usual
  1,000-year backoff. Further futile relaunches are possible at about A+1,000
  and A+3,000, both inside the horizon.
- With the policy on, the lock lasts until A+10,000 ≥ 35,500, beyond the
  horizon. So the policy can only remove futile launches.

**The cost bound for future domains** (for example Atlas-generated systems with
an opening habitability window):

- Suppose a destination is uninhabitable on [A₀, B), and a voyage is rejected
  at arrival year y in [A₀, B).
- Its earliest useful arrival is B.
- With the policy on, the earliest knowing relaunch arrives at
  y + 10,000 + travel or later.
- So the extra delay is max(0, y + 10,000 + travel − B), which is at most
  10,000 + travel years.
- Compared with policy off, the policy is worse only when B − y < 10,000.

There is one more effect. Arcs that launched before the news arrived can
still be rejected, and each such rejection restarts the 10,000 years from its
own arrival year. Own-lineage success at that body clears the memory, but an
uninhabitable window allows no such success.

**Decision for this round.** Keep 10,000 years. The guard test is the
tripwire: if a fixture ever introduces a temporary window, the test fails, and
the trade-off has to be revisited. Two options for that point:

1. split `uninhabitable` into `not-yet-habitable` and `doomed`, as the
   arriving voyage could observe;
2. cap the resurvey for temporary windows.

**Fixture caveat (not changed).** In `m4c-doomed-star-system.json`, the doomed
star's companion bodies `s00:b1` and `s00:b2` have `stellarDoomYear: null`.
They outlive their own star. If they were given the doom, their intervals would
also start at 25,500 and still be absorbing, so the theorem would still hold.
But evacuation would then have only interstellar targets, which need transport
tier 7. That is a scenario question for Kasper, not a resurvey risk.
